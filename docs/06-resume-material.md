# 简历与项目介绍材料

## 1. 项目名称

**微服务故障诊断与受控处置平台（个人项目）**

技术栈：Python、FastAPI、LangGraph、OpenTelemetry、Prometheus、Loki、Tempo、Kubernetes、PostgreSQL、Docker

## 2. 当前可用的简历表述

> 只有在模块实现并通过故障实验后，才能将以下完成时表述写入正式简历。当前工程处于设计阶段。

- 独立搭建可注入故障的微服务与可观测实验环境，基于 LangGraph 实现告警归并、调查规划以及 Metrics、Logs、Trace、Change 四类 Agent 的并行取证和有限迭代诊断。
- 设计统一 Evidence/Hypothesis 模型，为根因候选关联支持证据、反证、查询来源和置信度，遥测缺失或证据不足时自动降级至人工值班流程。
- 构建版本化 Runbook 注册表和隔离执行器，通过参数 Schema、RBAC、人工审批、资源版本检查、幂等键与审计日志约束 Kubernetes 重启、扩容和回滚操作。
- 建立慢查询、Redis 连接池耗尽和错误配置三类可重复故障实验，以根因 Top-K、MTTD/MTTR、证据可追溯率、安全拦截和单事件成本对比单 LLM 基线与多源证据方案。

实测后可把一条改写为：“在自建 N 服务实验环境和 M 次冻结故障实验中……”。必须同时说明样本规模，避免用小数据集百分比制造误导。

## 3. 30 秒项目介绍

“我做的是一个自建实验环境上的 AIOps Agent。Alertmanager 告警先归并为 Incident，协调器再并行调度指标、日志、Trace 和变更调查器。它们不会直接下结论，而是输出带查询来源和时间窗的结构化证据，再由根因节点结合支持与反证排序。处置只能选择注册 Runbook，经过独立策略、审批和最小权限执行器，最终用新的遥测窗口验证是否真的恢复。重点不是让模型执行命令，而是让诊断有证据、动作可控制、结果可验证。”

## 4. 两分钟介绍结构

1. **问题**：只把日志扔给 LLM 缺少跨数据源证据，且直接执行命令不可控。
2. **范围**：三个固定故障、四类只读调查器、三个 Runbook。
3. **架构**：事件状态图、并行调查、Evidence/Hypothesis、隔离执行、恢复验证。
4. **难点**：并行 state 合并、遥测查询限制、反证、审批恢复、动作幂等。
5. **验证**：故障真值、单 LLM 基线、重复实验、安全攻击用例、MTTD/MTTR。
6. **取舍**：牺牲任意故障通用性，换取安全性、可复现性和可解释性。

## 5. 项目真实性边界

- 必须使用“自建微服务实验环境”“故障注入”“实验结果”。
- 不把实验 MTTR 等同于真实企业生产 MTTR。
- 不虚构真实 on-call 团队、事故数量或线上集群规模。
- 面试时可现场注入故障并展示完整 trace，这是最强真实性证明。
