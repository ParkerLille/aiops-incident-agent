# 微服务故障诊断与受控处置平台：项目规格

## 1. 项目定位

这是一个针对研发效能/AIOps 场景的个人工程项目。它在自建微服务实验环境中接收 Prometheus 告警，查询 Loki、Tempo、Kubernetes 和部署记录，用结构化证据驱动根因排序，并在安全策略约束下执行预定义 Runbook。

系统定位为值班工程师的调查助手与受控自动化执行器，不承诺对任意故障自主修复。

## 2. 用户角色

| 角色 | 权限 |
|------|------|
| On-call Engineer | 查看事件、证据、根因与调查时间线 |
| Incident Commander | 调整事件级别、终止调查、指定处置方案 |
| Approver | 审批中高风险 Runbook |
| Platform Admin | 注册数据源、服务拓扑、Runbook 和权限策略 |
| Agent Service Account | 只读遥测；仅通过执行器获得受限写权限 |

## 3. 核心用户故事

### US-01 告警归并

多个相关告警在时间窗口内按服务、依赖关系和指纹合并为一个 Incident。重复 Webhook 不创建重复事件，事件时间线保留原始告警引用。

### US-02 并行调查

协调器根据受影响服务和症状生成有预算的调查计划。Metrics、Logs、Trace、Change 调查器只调用各自白名单查询工具，返回统一 `Evidence`，不能直接宣布最终根因。

### US-03 根因排序

分析节点基于支持证据与反证生成候选根因。每个候选项必须关联证据 ID、置信度和待验证问题；证据不足时继续一次定向调查或转人工。

### US-04 受控处置

处置规划器只能从注册 Runbook 中选择动作并填充参数。策略服务根据环境、服务、动作和风险要求审批；执行器再次验证审批、RBAC、幂等键和目标资源版本。

### US-05 恢复验证与复盘

执行后等待稳定窗口，比较错误率、P95、健康检查和 Pod 状态。未恢复则将“动作无效”作为新证据返回分析，不得直接关闭事件。恢复后生成包含时间线、根因、动作和后续项的复盘草稿。

## 4. 功能范围

### 必须完成

- Prometheus Alertmanager Webhook、去重和事件聚合。
- 服务拓扑、所有权和最近部署/配置变更查询。
- Prometheus、Loki、Tempo、Kubernetes 四类只读工具。
- 并行调查、证据标准化、根因 Top-K、有限循环。
- 三个类型化 Runbook、风险策略、人工审批、幂等执行和审计。
- 执行前 dry-run、执行后稳定窗口验证、失败回退。
- 三个可复现故障场景及对应 ground truth。
- 离线/在线实验评测和 Agent 自身可观测性。

### 明确不做

- 不接入真实生产集群，不保存真实公司日志。
- 不允许任意 Shell、任意 PromQL/LogQL 或任意 Kubernetes Patch。
- 不建设通用 CMDB、完整 PagerDuty 替代品或通用自愈平台。
- 首版不做容量预测、异常检测模型训练和跨集群调度。
- 不将 LLM 的自然语言结论直接作为执行授权。

## 5. 非功能要求

| 类别 | 要求 |
|------|------|
| 安全 | 调查身份默认只读；所有写动作经过独立执行服务 |
| 可追溯 | 结论、查询、证据、审批、动作和验证共享 incident/trace id |
| 可恢复 | 长时间调查和待审批事件在服务重启后恢复 |
| 有界执行 | 调查轮数、时间、查询数据量、Token 与费用均有预算 |
| 幂等 | 重复告警、审批回调和 Runbook 请求不会产生重复副作用 |
| 证据质量 | 每条 Evidence 保存来源、窗口、查询、观测和置信度 |
| 数据保护 | 日志查询结果限制字段、行数和时间范围，并做 Secret 脱敏 |
| 可测试 | 调查器可使用固定遥测 Fixture，执行器可使用 Fake Kubernetes |

## 6. 成功标准

1. 三个故障均可一键注入、触发告警、完成调查并验证恢复。
2. 根因结果能定位到真实遥测查询，禁止无证据的最终结论。
3. 所有未授权、参数越界和过期审批动作被 100% 拦截。
4. 服务重启后待审批事件可恢复，重复恢复不重复执行 Runbook。
5. 相同故障集上完成单 LLM 基线与多源证据方案对比。
6. 报告明确记录实验集群规格、随机种子、数据窗口和模型版本。

## 7. 演示脚本

向实验集群发布带慢查询的 Order Service，观察告警归并与四路并行调查，打开原始 PromQL/LogQL/Trace/Deployment 证据，查看根因排序，提交回滚审批，在审批期间重启 Agent 服务，批准后恢复执行，观察稳定窗口验证和复盘报告。最后尝试篡改目标 namespace，展示策略拒绝。
