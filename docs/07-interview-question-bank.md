# 面试追问题库

## 多 Agent 与编排

### 1. 为什么这个项目适合多 Agent？

指标、日志、Trace 和变更记录具有独立数据源、工具和判断方法，可以并行执行并用统一 Evidence 合并。它们的边界来自职责与权限，而不是为了展示“多个角色”。根因裁决和执行权限仍然集中控制。

### 2. 并行节点如何安全合并 state？

每条 Evidence 有基于 task/source/window/content hash 的稳定 ID，LangGraph reducer 按 ID 去重并验证 incident id。节点只返回新增证据，不修改其他调查器的状态；重试因此保持幂等。

### 3. 如何避免调查循环失控？

状态保存 round、deadline、query budget、Token budget 和 cost budget。首次证据不足只能生成有明确缺口的定向任务；达到任一预算即转人工并输出已知/未知信息。

### 4. Agent 之间结论冲突怎么办？

调查器不提交最终结论，只提交 Evidence。Hypothesis 显式关联 supports 和 contradicts，协调器针对能区分候选根因的缺口发起查询，不能用多数投票替代证据。

## 遥测与根因

### 5. 为什么不允许模型自由写 PromQL/LogQL？

自由查询可能产生高基数、大时间窗和昂贵扫描，也可能越权读取。模板注册表将可查询服务、参数、窗口和返回量限制在可测试范围；新增模板通过代码评审扩展。

### 6. Evidence 为什么要保存 query hash 和时间窗？

同一句“错误率上升”在不同窗口可能完全不同。时间窗和查询来源支持重放、审计与重复实验；hash 避免把敏感或过大的完整查询长期放入 checkpoint。

### 7. 如何区分相关性和根因？

候选根因必须解释受影响组件、时间先后和传播路径，并同时检查反证。例如最近发布只构成相关性，还需 Trace/日志证明新路径发生异常，恢复验证也必须与处置一致。

### 8. 某个遥测源不可用怎么办？

工具返回结构化 missing-source，而不是空字符串。根因置信度和最小证据策略会考虑缺失；无法满足门槛时转人工，并列出缺少的数据源。

### 9. 为什么需要服务拓扑快照？

它帮助聚合关联告警和限定调查范围，也避免调查期间拓扑变化导致前后证据语义不一致。Incident 引用创建时的快照，同时单独记录后续拓扑变化。

## 安全执行

### 10. 为什么不能让模型生成 kubectl 命令再审批？

审批人很难可靠审查任意命令的所有副作用。注册 Runbook 有固定参数 Schema、权限、风险、超时和验证策略，执行器使用 Kubernetes Client 类型化调用，显著缩小攻击面。

### 11. 调查服务和执行器为什么要分开？

调查需要读取较多遥测但不需要写集群；执行器只需少量 Kubernetes verbs。分离进程和 ServiceAccount 后，即使 Prompt 注入影响调查 Graph，也拿不到写凭证。

### 12. 审批后资源已经变化怎么办？

执行命令保存目标 resource UID/version，执行前重新读取并比较。发生变化则使审批失效，要求重新 dry-run 和审批，避免对错误版本执行旧计划。

### 13. Kubernetes API 超时，如何避免重复回滚？

先检查幂等执行记录和目标 rollout 状态，不能立刻再次调用。相同键相同参数返回已有状态；无法确认时进入人工处理。执行接口的成功不等于 Incident resolved。

### 14. 什么动作可以自动执行？

首版仅 lab 环境的低风险、可逆、目标明确动作可自动；回滚和扩容默认审批。生产配置即使存在也默认全部审批。自动化级别由策略服务决定，不由 LLM 置信度单独决定。

## 恢复与评测

### 15. 如何判断真的恢复？

执行后等待新稳定窗口，用确定性策略检查错误率、P95、健康检查和副本状态。瞬时下降不算恢复；无数据返回 inconclusive。只有 successful VerificationResult 能关闭事件。

### 16. MTTD 和 MTTR 如何定义？

MTTD 从首个告警进入系统到首次产生达到阈值且正确的根因；MTTR 到稳定窗口验证恢复。审批等待时间单独报告，否则无法区分 Agent 诊断耗时和人为等待。

### 17. 如何构造可信评测集？

每个故障由显式开关注入并保存 ground truth，同时加入无关发布和 warning 作为干扰。相同镜像、流量和窗口至少重复五次，报告离散度与失败案例，不只报告最好一次。

### 18. 多 Agent 一定比单 Agent 好吗？

不一定。多 Agent 增加调用次数、成本和状态合并复杂度。该项目用相同模型与故障集比较单 LLM 基线；只有诊断质量或时间收益覆盖成本时才保留并行分解。

### 19. 最难实现的部分是什么？

不是 Prompt，而是稳定的故障实验、遥测时间对齐、证据真值和动作幂等。没有可重复实验就无法判断 Agent 是否真的改进，因此先建设 lab 再优化推理。

### 20. 真实生产化还缺什么？

需要对接企业 CMDB/IdP/变更平台，执行器安全评审，跨集群隔离，审计留存，灾备，查询容量治理，真实事故回放和 on-call 反馈闭环。个人项目只证明核心机制和工程方法。
